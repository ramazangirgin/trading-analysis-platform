# Plan: Automated check of the uppercase database object names

- **Issue**: #115 (Automated check: uppercase database object names)
- **Plan**: 1 of 1 for this issue; depends on: none (#113 / PR #114 and #112 are merged)
- **Version bump**: minor (docs/coding-convention/repository-versioning-and-releases.md)

## Goal

A test in `mise run build` reads the PostgreSQL catalog after every migration has run and fails
on any database object name that breaks
[backend-database-naming.md](../docs/coding-convention/backend-database-naming.md): a table,
column, constraint, index or enum type whose name is not uppercase, or a constraint or index whose
name does not follow `<TABLE>_PK`, `<TABLE>_<COLUMN>_FK`, `<TABLE>_<COLUMNS>_UK` or
`<TABLE>_<COLUMNS>_IDX`, which is also how a name generated by PostgreSQL shows up. The reviewer
no longer checks new migrations by eye, and the convention names the check that enforces it.

## Design

### Decisions taken while planning

- **The stored catalog is the only check.** Item 3 of the issue (a SQL linter on the migrations,
  or a Checkstyle check on SQL in Java) is not done. Since #112 the code has no SQL of its own (JPA
  only, no `Jdbc*Adapter` left), and entity names are already validated against the schema by
  `ddl-auto=validate`. The catalog test catches every wrong name in a migration in
  `mise run build`. A SQL linter would add a tool to the hook for five files. The reason goes into
  the naming document's "Why".
- **NOT NULL constraints are exempt.** PostgreSQL 18 stores every `NOT NULL` as a constraint of its
  own (`pg_constraint.contype = 'n'`) named `<TABLE>_<COLUMN>_not_null`. Checked on
  `postgres:18.6` with V1–V5, there are 40 of them today. They are column properties, written as
  `NOT NULL` in the column definition, and their generated name already starts with the uppercase
  table and column. The check skips them, and the naming document says so.
- **Flyway's history table: only its name is ours.** `FLYWAY_SCHEMA_HISTORY` is checked like any
  table name. Its columns (`installed_rank`, `version`, …), its primary key
  `FLYWAY_SCHEMA_HISTORY_pk` and its index `FLYWAY_SCHEMA_HISTORY_s_idx` are created by Flyway in
  lower case and cannot be configured, so the check skips everything inside that table. The naming
  document says so.

### The check: `DatabaseNamingCheck`

A package-private class in the `:backend` tests,
`artifact/backend/src/test/java/tr/girgin/backend/trading/analysis/platform/DatabaseNamingCheck.java`.
It takes a `javax.sql.DataSource` and returns the list of violations, one readable line each, for
example `index "analyses_bad_idx" on table "ANALYSES": not uppercase`, in a stable order (sorted)
so a failure lists all of them at once.

It reads schema `public` with plain JDBC (`java.sql`). The catalog has no entities, so the
"checks go through the ports" rule of the persistence tests cannot apply. `org.springframework.jdbc`
stays banned (Checkstyle `IllegalImport`), and the persistence document records the exception (see
"Docs to update"). Sources:

| Object | Catalog | Rule |
|---|---|---|
| Table | `information_schema.tables` (`table_type = 'BASE TABLE'`) | Uppercase |
| Column | `information_schema.columns` | Uppercase (none of `FLYWAY_SCHEMA_HISTORY`'s) |
| Constraint | `pg_constraint` joined to its table, with `contype` and the names of the `conkey` columns | Skipped: `contype = 'n'` and the history table's. Primary key (`p`): exactly `<TABLE>_PK`. Foreign key (`f`): exactly `<TABLE>_<COLUMNS>_FK`, the key's columns joined by `_` in key order (one column today). Unique (`u`): `<TABLE>_…_UK`. Any other kind (check, exclusion): a violation saying the convention has no name for it yet, so adding one starts with the naming document |
| Index | `pg_indexes` with `pg_index` (`indisprimary`, `indisunique`) | Skipped: the history table's. Uppercase. Primary-key index: `<TABLE>_PK`. Other unique index: `<TABLE>_…_UK`. Any other index: `<TABLE>_…_IDX`. An index that backs a constraint has the constraint's name, so both checks agree |
| Enum type | `pg_type` with `typtype = 'e'` in `public` | Uppercase |

"Uppercase" means the name matches `[A-Z0-9_]+`, the convention's alphabet. A name that PostgreSQL
generated or that was written unquoted fails it (`analyses_pkey`, `orders`), and so does a generated
suffix on an uppercase table (`"ORDERS_pkey"`, `"ORDERS_TICKER_idx"`). The prefix checks compare
with the table's stored name, so a constraint named after another table fails too.

The check also returns what it saw (the table names), so a test can assert that it did read the
schema. An empty selection never passes silently (the convention README's "Changing a convention",
point 3).

### The tests

1. **`DatabaseNamingTest`** (`@SpringBootTest`, in the same package): the application's own
   schema. It starts the application on a fresh database the way `TradingPlatformApplicationTests`
   does (`TestPlatformHome.create()` / `register(...)`), so Flyway runs with the application's own
   configuration (`spring.flyway.table`) and every migration on the application's classpath: the
   three domains' adapters and any future one. It autowires the `DataSource` and asserts:
   - the check saw at least `ANALYSES`, `PRESETS`, `USERS`, `ROLES`, `USER_ROLES` and
     `FLYWAY_SCHEMA_HISTORY`;
   - the list of violations is empty, and a failure prints every one of them.
   The schema produced by #112's mapping is the migrations' schema (`ddl-auto=validate` creates
   nothing), so this covers it.
2. **`DatabaseNamingCheckTest`** (plain JUnit, same package): proves the check fails on a bad
   migration. On a fresh `PostgresTestDatabase` it runs
   `TestMigrations.migrate(dataSource, null, "classpath:db/naming-violations")`, which is every real
   migration (V1–V5) plus a test-only `V900__naming_violations.sql`. It asserts that the
   violations are exactly the fixture's, so the real migrations add none:
   - `CREATE TABLE orders (...)`: an unquoted table, lower case;
   - a quoted uppercase table with a lower-case column `"ticker"`;
   - inline `PRIMARY KEY`, `UNIQUE` and `REFERENCES "ANALYSES" ("ID")`, which PostgreSQL names
     `…_pkey`, `…_key` and `…_fkey`;
   - `CREATE INDEX ON "…" ("…")` with no name (generated `…_idx`);
   - an explicit but wrong name: `"…_KEY"` for a primary key, an `_FK` named after another column,
     a unique index without `_UK`, an index with another table's prefix;
   - a named `CHECK` constraint (no rule for it yet);
   - `CREATE TYPE mood AS ENUM (...)` (unquoted enum type);
   - one correct table (named constraints and index, `NOT NULL` columns), which yields no violation:
     the NOT NULL exemption and the rules' acceptance are shown, not only their rejections.
   The fixture lives in `artifact/backend/src/test/resources/db/naming-violations/`, never in
   `db/migration`, so the application and the Spring Boot tests do not pick it up. Its header
   comment says it is a test fixture for `DatabaseNamingCheckTest` and never applied anywhere
   else.

Both need Docker or Podman, like the other repository tests. They run in `./gradlew :backend:test`,
part of `mise run build` and CI's *Backend and frontend* job. No new library: `java.sql`
and `javax.sql` are in the JDK, `PostgresTestDatabase`, `TestMigrations` and the PostgreSQL driver
come from `testFixtures(project(":backend:library:persistence"))`. If the dependency analysis
reports a library the new tests use but `:backend` does not declare, declare it as
`testImplementation`, as the analysis asks.

## Out of scope

- A SQL linter on the migrations or a Checkstyle check on SQL in Java (item 3 of the issue):
  decided against above.
- Naming the NOT NULL constraints explicitly (`<TABLE>_<COLUMN>_NN`): decided against above. It
  would need a rename migration and a fifth suffix.
- Running the check in each adapter module's own tests: the `:backend` test sees every migration
  on the application's classpath, which is enough.
- Rules for check and exclusion constraints, sequences and views: none exist today. The check
  reports a named check constraint as "no rule yet", so the first one starts with the naming
  document.
